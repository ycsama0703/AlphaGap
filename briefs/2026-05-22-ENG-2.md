# 双层多智能体架构可提升金融工具调用中的约束感知规划和合规性检查能力。

## 1. The Core Insight

金融工具调用中，合规约束（权限、风险预算、监管规则）是硬性、非协商性的，而现有 LLM agent 框架（ReAct、单智能体）将约束视为可选的上下文提示，导致违规频发。AI 侧最近的结构化多智能体协作架构（如 2604.27221）通过“上层规划-下层执行-验证反思”的双层分解和共享工作空间，天然适合将“约束”从隐式上下文提升为显式、可审计的检查层。因此，将这种架构迁移到金融工具调用，有望将合规性从“希望 agent 记住”变为“系统强制检查”。

## 2. Conceptual Mapping (AI ↔ Fin)

- **AI 侧结构**：双层多智能体系统（2604.27221）。上层（Planner）将复杂查询分解为子任务并分配约束；下层（Executor）并行执行子任务；验证层（Verifier）检查结果是否符合约束，若违规则触发反思（Reflection）并反馈给上层重新规划。共享工作空间记录所有约束历史，避免重复违规。
- **Fin 侧对应结构**：金融工具 API 调用链。一个用户查询（如“买入 100 股 AAPL，但风险预算不超过 5%”）需要分解为多个工具调用（查询账户余额、检查权限、获取报价、执行订单），每个调用都有对应的权限、风险限额、合规规则。
- **匹配状态**：match。结构高度同构——金融工具调用天然是“任务分解 + 约束检查”的流程。上层规划对应交易策略分解，下层执行对应具体 API 调用，验证层对应合规审查。
- **Bridge 如何搭**：不需要改造架构，只需将金融领域的约束规则（权限矩阵、风险限额、监管规则）编码为 Verifier 的检查函数。关键设计决策是：约束规则是硬编码（确定性规则引擎）还是由 LLM 判断（软约束）？建议混合——硬约束（如“交易员 A 不能交易衍生品”）用规则引擎，软约束（如“风险预算是否合理”）用 LLM 判断。

## 3. Data Requirements (shape, not acquisition)

- **维度**：多轮对话 + 工具调用轨迹。每个样本是一个 (query, tool_call_sequence, constraint_violations, final_result) 四元组。
- **必需特征类型**：
  - 用户查询（自然语言）
  - 工具定义（名称、参数 schema、权限要求、风险限额）
  - 约束规则集（权限矩阵、风险预算、监管规则）
  - 正确/违规的调用轨迹（用于评估）
- **时序长度 / 样本量**：
  - 最少需要 100 个查询（覆盖 5-10 种约束类型）才能看到统计意义。
  - 每个查询需要 3-8 步工具调用，形成完整轨迹。
  - 约束违规样本至少占 20%，否则模型会偏向“无违规”模式。
- **标签来源选项**：
  - **FinToolBench (2603.08262)**：760 个真实金融工具和查询，但缺乏显式约束标签。需要人工标注合规性（成本高，但可控）。
  - **FinMCP-Bench (2603.24943)**：基于 Model Context Protocol，工具定义更结构化，但同样缺乏约束标签。
  - **自建**：从 Bloomberg Terminal API 子集或券商 API 文档中提取工具定义，人工构造带约束的查询。优点：约束可控；缺点：规模小。
  - **推荐**：以 FinToolBench 为基础，人工添加约束规则（权限、风险预算）并标注违规情况。这是最平衡的选择。

## 4. Benchmark Landscape

这个方向（金融 LLM agent 的约束感知）目前处于早期，学术版图可划分为三个流派：

1. **通用 ReAct 流派**（Yao et al. 2023, FinToolBench 默认方法）：
   - 核心假设：LLM 通过上下文学习可以隐式处理约束。
   - 代表工作：ReAct, Reflexion, FinToolBench baseline。
   - 局限：约束是隐式的，LLM 容易遗忘或误解；无审计轨迹。

2. **结构化工具调用流派**（FinMCP-Bench, ToolLLM）：
   - 核心假设：通过结构化工具定义（如 OpenAPI schema）和函数调用机制，可以提升工具调用准确性。
   - 代表工作：FinMCP-Bench, ToolLLM, Gorilla。
   - 局限：关注工具调用准确性，而非合规性；约束仍作为参数传递，无独立检查层。

3. **规则引擎增强流派**（金融合规系统，如 Bloomberg AIM, Charles River）：
   - 核心假设：合规性必须由确定性规则引擎保证，LLM 只负责自然语言理解。
   - 代表工作：传统金融合规系统（非 LLM）。
   - 局限：规则引擎无法处理模糊或上下文相关的约束；缺乏灵活性。

**本 gap 的定位**：属于新流派——**多智能体约束感知流派**。它结合了流派 1 的灵活性（LLM 理解自然语言查询）、流派 2 的结构化工具调用（函数调用机制）和流派 3 的确定性检查（Verifier 层）。差异化在于：将约束检查从 LLM 的隐式推理中剥离，交给专门的 Verifier 智能体，同时通过共享工作空间实现约束历史的可审计性。

## 5. Where to Start (Reading + Replication Order)

**第 1 步：读透核心论文（1-2 天）**
- 先读 **2604.27221**（Web2BigTable），理解双层多智能体架构的具体实现：Planner 如何分解任务、Verifier 如何检查、Reflection 如何触发。重点看共享工作空间的设计。
- 再读 **2603.08262**（FinToolBench），理解金融工具调用的数据格式、评估指标和 baseline 方法。重点看工具定义和查询结构。
- 可选：读 **2603.24943**（FinMCP-Bench），了解 Model Context Protocol 如何结构化工具调用。

**第 2 步：复现 baseline 确认环境 work（1 周）**
- 在 FinToolBench 上复现 ReAct baseline（单智能体 LLM 直接调用工具）。确认工具调用准确率和任务成功率可复现。
- 这一步的目的是：确保你的工具调用环境、LLM API 调用、评估脚本都 work。不要跳过。

**第 3 步：第一个真实验（2 周）**
- **最小可行实验**：选 10 个 FinToolBench 查询，人工添加 3 种简单约束（如“不能查询衍生品数据”、“风险预算不超过 10%”、“需要双重授权”）。
- 实现一个最简单的双层架构：上层 Planner（GPT-4）将查询分解为子任务并分配约束；下层 Executor（GPT-4）调用工具；Verifier（规则引擎 + GPT-4 判断软约束）检查结果。
- 测量：任务成功率 vs 合规违规次数。对比 ReAct baseline。
- **如果过了**（合规违规次数降低 50% 以上，任务成功率下降不超过 10%）：扩展到 100 个查询，添加更多约束类型，加入共享工作空间和 Reflection 机制。
- **如果不过**（合规违规次数无显著改善）：检查约束编码是否正确。如果 Verifier 过于严格导致任务失败率高，尝试将硬约束和软约束分开处理（硬约束用规则引擎，软约束用 LLM 判断）。

**Compute / Runtime**：
- **主要需求**：LLM API（GPT-4 或 Claude 3.5）。每个查询需要 5-15 次 API 调用（Planner 1 次 + Executor 3-8 次 + Verifier 1-3 次 + Reflection 0-2 次）。
- **估算**：100 个查询 × 10 次调用 = 1000 次 API 调用。GPT-4 成本约 $0.03/次 → $30。运行时间：数小时（主要受 API 延迟限制）。
- **主要瓶颈**：LLM API 调用次数和约束规则编码的准确性。多智能体协调增加延迟（每个查询可能需 30-60 秒）。
- **低算力 fallback**：先用 10 个查询和简单约束验证机制（规则引擎 + GPT-3.5）。成本降至 $1-2。如果验证机制有效，再升级到 GPT-4。

## 6. The True Contribution

- **(a) Empirical contribution**：第一次系统性地证明，在金融工具调用中，将合规约束从 LLM 的隐式推理中剥离并交给专门的 Verifier 智能体，可以显著降低违规次数（相比 ReAct 和单智能体 baseline），同时保持可接受的任务成功率。提供第一个包含约束感知的金融工具调用 benchmark（FinToolBench 的约束增强版）。
- **(b) Methodological contribution**：提出一个可迁移的“双层多智能体 + 约束检查”框架，将 AI 侧的结构化多智能体协作架构（2604.27221）适配到金融领域。关键设计模式包括：硬约束 vs 软约束的混合检查策略、共享工作空间中的约束历史审计、以及 Reflection 机制对违规的自动修复。
- **(c) Theoretical contribution**：在“LLM agent 安全部署”的 framework 下，提出了“约束显式化”原则——即对于高风险领域（金融、医疗、法律），合规约束不应作为 LLM 的隐式上下文，而应作为系统级的显式检查层。这为 LLM agent 在受监管行业的部署提供了设计原则。

## 7. Conceptual Risks

- **致命风险**：**约束规则编码可能遗漏金融领域特定合规要求**。金融合规规则极其复杂（如 Reg T、SEC Rule 15c3-3、MiFID II），且不同机构、不同产品、不同司法管辖区规则不同。如果 Verifier 只覆盖了表面规则，实际部署时仍会违规。**Mitigation**：与金融合规专家合作，从 Bloomberg AIM 或 Charles River 的规则库中提取真实约束规则。在论文中明确声明“本框架不保证覆盖所有合规要求，仅作为 proof-of-concept”。

- **重要风险**：**Verifier 过于严格导致任务失败率高**。如果 Verifier 对软约束（如“风险预算是否合理”）判断过于保守，会导致大量任务被拒绝，降低实用性。**降级路径**：将 Verifier 的严格程度作为可调参数（如 strictness threshold），在论文中展示不同阈值下的 trade-off（任务成功率 vs 合规违规次数）。如果 trade-off 太差，承认“当前 Verifier 设计需要进一步优化”。

- **可接受风险**：**多智能体协调增加延迟**。每个查询需要多次 LLM API 调用，延迟可能从秒级增加到分钟级。这在实时交易场景中不可接受，但在分析场景（如投资组合构建、合规审查）中可接受。论文中明确讨论延迟 trade-off，并指出“对于实时场景，需要优化为单次调用或并行调用”。

## 8. Success Story (Paper Headline)

**标题**：ConstrainedAgent: A Bi-Level Multi-Agent Framework for Compliance-Aware Financial Tool Use

**3 个 Core Figure**：
1. **Figure 1: 架构图**。展示双层多智能体系统：上层 Planner 接收用户查询并分解为子任务（带约束标签），下层 Executor 并行调用工具，Verifier 检查结果并触发 Reflection。共享工作空间记录所有约束历史。对比 ReAct 的单智能体架构（无显式约束检查）。
2. **Figure 2: 主要结果**。柱状图对比 ReAct、单智能体 LLM、ConstrainedAgent 在 FinToolBench 约束增强版上的表现。Y 轴左：任务成功率（越高越好），Y 轴右：合规违规次数（越低越好）。ConstrainedAgent 在违规次数上降低 60-80%，任务成功率下降 5-10%。
3. **Figure 3: Ablation 分析**。展示去掉 Verifier、去掉共享工作空间、去掉 Reflection 后的性能变化。关键发现：Verifier 是降低违规的核心（贡献 70%），共享工作空间减少重复违规（贡献 20%），Reflection 修复剩余违规（贡献 10%）。

**Abstract Teaser**：
> “Financial LLM agents must navigate complex compliance constraints—permissions, risk limits, regulatory rules—that existing tool-use benchmarks (FinToolBench, FinMCP-Bench) largely ignore. We introduce ConstrainedAgent, a bi-level multi-agent framework that decomposes user queries into sub-tasks, executes tool calls in parallel, and explicitly verifies compliance via a dedicated Verifier agent with a shared workspace for constraint history. On a compliance-augmented version of FinToolBench, ConstrainedAgent reduces compliance violations by 68% compared to ReAct baselines while maintaining 92% of task success rate. Our ablation study reveals that the Verifier agent is the primary driver of compliance improvement, while the shared workspace prevents repeated violations across sub-tasks.”
